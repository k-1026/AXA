# 챗봇·에이전트 응답시간: 보통 얼마인가, 우리는 어디쯤인가 (2026-11-26, 원문 확인판)

## 결론 (짧게)
- **"에이전트 서비스별 질문 응답시간 평균"을 공개한 공식·통계 자료는 없다 → 미확인.** 피클·Manus·ChatGPT 에이전트 모두 공식 평균 수치가 없다. 있는 것은 회사 FAQ의 범위, 기자 체험기, 설문뿐이다
- 응답이 느린 에이전트는 두 종류로 나뉜다
  1. **대화형 (사용자가 화면 앞에서 답을 기다림)**: 10초 넘으면 주의가 흩어진다 (NN/g). 1초 넘으면 "작업 중" 표시, 10초 넘으면 진행률 표시와 중단 방법이 필요하다
  2. **작업 위임형 (맡기고 다른 일을 함)**: 몇 분 ~ 몇 시간도 받아들여진다. 피클(체험기 2시간 15~18분, 본인인증 대기 포함), Manus(공식 2~5분 / 10~30분). 운영 중인 에이전트 팀의 66%가 몇 분 이상 응답을 허용한다
- **"백그라운드에서 돌고 다른 걸 해도 괜찮다"는 생각은 2번 유형에서는 근거가 있다.** 다만 우리 챗봇의 대부분 턴은 "되묻고 답하는" 1번 유형이다 (진료과 → 병원 → 날짜 → 국적 → 비자 질문). 이 턴들을 백그라운드로 돌리면 사용자가 질문 하나에 답할 때마다 돌아와야 한다

## 1. 대화형 기준 (원문 확인)
| 시간 | 의미 (NN/g) | 권고 |
|---|---|---|
| 0.1초 | 즉시 반응했다고 느끼는 한계 | 결과만 보여 주면 됨 |
| 1초 | 생각 흐름이 끊기지 않는 한계 | 1초 넘으면 "작업 중" 표시 |
| 2~10초 | — | 바쁜 커서 + 바뀌는 숫자 정도 (진행률 막대까지는 과함) |
| 10초 | 주의를 붙잡아 두는 한계 | 10초 넘으면 **진행률 표시 + 중단할 수 있는 방법** |

- **CHI '26 연구 (NYU, 2026-04-23 보도, 참가자 240명)**: 챗봇 답을 2초·9초·20초 뒤에 보여 줬다. 기다린 시간이 달라도 질문 횟수는 비슷했다. 오히려 **2초 만에 답을 받은 쪽이 답을 "덜 사려 깊고 덜 유용하다"고 평가**했다. 긴 멈춤을 AI가 "생각하는 중"으로 받아들인 경우가 많았다
  → 무조건 빠른 게 좋다는 뜻은 아니다. 다만 20초까지만 실험했다
- 처음 판에 넣었던 두 논문(Kim·Shams·Kim 2025, BISE 2022)은 원문을 열 수 없어 이 판에서 뺐다 (인증서 만료 · 로그인 필요) → 미확인

## 2. 작업 위임형: 서비스별 확인된 시간
| 서비스 | 시간 | 근거 등급 | 비고 |
|---|---|---|---|
| **피클 (Pickle)** | 쇼핑 첫 요청 → 결제 완료 **약 2시간 18분**, 열차 예매 **약 2시간 15분** | 언론 (체험기 1건) | 기자의 외부 미팅, 서버 연결 지연, **본인인증 대기가 포함된 시간**이라 AI 처리 시간이 아니라고 기사가 직접 밝힘 |
| 피클 | "다른 플랫폼과 연결하고 답변하는 시간이 상당히 오래 걸렸다" (분 단위 수치 없음) | 언론 | 경향신문 |
| 피클 | 분 단위 수치 없음 | 언론 | 아이뉴스24 체험기. 결제·예약처럼 되돌리기 어려운 작업은 진행 전에 사용자 확인 |
| **Manus** | 간단한 발표자료 **2~5분**, 리서치 보고서·웹사이트 **10~30분** | 공식 (회사 FAQ) | "진행 상황을 실시간으로 볼 수 있다" |
| ChatGPT 에이전트 | 공식 수치 못 찾음 → 미확인 | — | 블로그 비교글은 서로 숫자가 달라 쓰지 않음 |

**피클이 기다리는 시간을 다루는 방식 (체험기 기준)**
- 보안 단계(카드사 인증, 결제 비밀번호)에서는 **화면을 사용자에게 넘긴다**
- 결과(승차권, 영수증)는 **채팅창으로** 보낸다. 사용자가 결제를 미루자 다시 예약을 확인해 자리를 확보했다
- 다음 날 아침 스스로 메일을 확인해 "아직 답장이 없다"고 알려 준 사례가 있다 (먼저 알려 주는 방식)
- 푸시 알림·백그라운드 동작에 대한 공식 설명은 찾지 못했다 → 미확인 (pickle.com 초대 페이지에는 설명이 없음)

## 3. 업계 실제 (원문 확인)
| 자료 | 내용 |
|---|---|
| **Measuring Agents in Production** (arXiv 2512.04123 v3, 2026-02-03, UC Berkeley·Stanford·IBM Research 등) | 운영·시범 중인 에이전트 응답자 중 **66%가 몇 분 이상 응답 허용, 17%는 제한 없음** (이 문항 N=53). 사례 20개 중 **15개는 비동기로 동작**, **실시간이 필요한 건 5개** (주로 음성). 설문 306명, 2025-07-28~10-29 |
| **State of Agent Engineering** (LangChain, 2025-11-18~12-02 설문, 1,340명) | 운영 장벽 1위 품질 32%, **2위 latency 20%**. 직원 2천 명 이상 기업에서는 보안(24.9%)이 2위 |
| 에이전트 프레임워크 비교 (DEV Community, 2026-02-18, 개인 블로그) | 도구 1번 부르는 단일 단계 에이전트, 평균 **5.7초(Rust) ~ 10.2초(LangGraph)**. 대부분 LLM 왕복 시간. 글쓴이가 1위 프레임워크 제작자이고, 사용 모델을 글 안에서 다르게 적음(gpt-5.1 / gpt-4o-mini) → 참고만 |

## 4. 우리 챗봇에 적용하면
| 우리 측정 | 시간 | 어느 유형 기준으로 볼까 |
|---|---|---|
| 배포 서버, 사용자 4턴 (11/25) | 7~15.4초 | 대화형 → 10초 기준 근처·초과 |
| 로컬 시나리오, 생각 켬 | 턴 평균 6~7초, 예약 턴 최대 14초 | 대화형 |
| NVIDIA 지연이 튄 경우 | 34·68·80초 | 대화형으로는 너무 김 |

**제안 (팀 결정 필요)**
1. **질문·답 턴은 대화형으로 둔다.** 목표: 보통 5초 안, 여러 단계 10초 안. 10초를 넘을 수 있으면 단계 표시("병원을 찾는 중…", "요청서를 만드는 중…")를 보여 준다. CHI '26 결과처럼 짧은 기다림은 "생각하는 중"으로 받아들여질 수 있어서, 단계 표시만 잘 보여 줘도 체감이 나아진다
2. **피클처럼 백그라운드로 돌릴 만한 것은 "사용자 입력이 더 필요 없는 일"이다.** 예: 병원이 확정·거절·시간 제안을 했는지 알려 주기, 요청서 제출 뒤 상태 변화. 우리 앱에는 이미 알림함(`/me/notifications`)이 있어 이쪽으로 보내면 된다
3. 진료과·날짜·국적처럼 되묻는 턴을 백그라운드로 돌리면 사용자가 질문마다 돌아와야 한다 → 맞지 않는다
4. 어떤 경우에도 20~30초 안에 답이나 "지연 중" 안내가 나오게 한다 (타임아웃·재시도 줄이기, 응답속도 점검 문서 6절 1번)

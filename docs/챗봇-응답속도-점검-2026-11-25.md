# 챗봇 응답 속도 점검 (2026-11-25)

배포 서버에서 챗봇 답이 너무 늦게 온다는 문제를 점검했다. LLM 호출 시간과 가드레일을 함께 봤다.

## 결론 (짧게)
- **가드레일은 원인이 아니다.** `ai/llm/safety.py`는 정규식 검사만 하고 LLM을 부르지 않는다. 측정값은 한 턴에 0.1~0.5ms. guard에 걸려도 LLM 호출이 늘지 않는다 (지시 한 줄만 덧붙음)
- **시간의 99% 이상이 LLM 호출이다.** 한 턴에 LLM을 2~3번 부르고, 한 번에 1~6초 걸린다 → 한 턴에 2~10초
- 배포 서버에서는 여기에 **콜드 스타트**와 **DB 조회**가 더해진다. 제공자가 응답하지 않으면 **최악의 경우 몇 분**까지 걸릴 수 있다 (아래 4번)

## 1. 측정 (로컬, 배포와 같은 순서 `LLM_PROVIDER_ORDER=nemotron,gemini`, 가상 병원 데이터)

| 턴 | 사용자 말 (요약) | 전체 | LLM 호출 | 가드레일 | 도구 |
|---|---|---|---|---|---|
| 1 | 수성구 여드름 흉터 | 7.5초 | 3번 (1.7 / 3.6 / 2.3초) | 0.1ms | 0.1ms |
| 2 | 추천해 줘, 12월 4일 | 2.4초 | 2번 (1.4 / 1.0초) | 0.5ms | 0.0ms |
| 3 | 일주일 방문 | 5.5초 | 3번 (1.3 / 1.3 / 2.9초) | 0.2ms | 0.1ms |
| 4 | 첫 번째 병원 12/4 10시 예약 | 9.8초 | 2번 (5.0 / 4.8초) | 0.1ms | 0.1ms |
| 5 | 레이저 안전? 부작용? (guard 걸림) | 6.2초 | 1번 (6.2초) | 0.4ms | — |

- 모든 호출에서 nemotron-3.5-super가 답했다 (fallback 없음)
- LLM을 부를 때마다 입력 토큰이 4,500~5,500개다. 시스템 프롬프트 약 6,800자에 도구 12개의 설명 약 6,400자가 **매번 다시** 들어간다. 도구 설명은 대부분 한국어라 토큰이 더 많이 든다
- 출력이 길수록 느리다. 출력 토큰 70개 → 1.0초, 500~680개 → 4.8~6.2초. 마지막 답변 문장이 길다

## 3. 가드레일 구조 (확인 결과)
`ChatService.ask` → `Orchestrator.handle` → `safety.check(텍스트)` 순서로 돈다. `safety.check`는 세 단계다.
1. 응급 단어 → block. LLM 없이 119 고정 문구 (가장 빠름)
2. 개인정보 정규식 마스킹
3. 의료 판단·평판·비자 정규식 → guard. 이번 턴 프롬프트에 지시 한 줄 추가
→ 모두 코드 검사라 속도에 영향이 없다. LLM이 답한 뒤 다시 검사하는 단계(후처리 LLM)는 없다.

## 4. 최악의 경우 (제공자가 느리거나 응답이 없을 때)
`ai/llm/config.py` 기본값: `llm_timeout_seconds=30`, `llm_max_retries=2`, 모델 4개(nemotron 2개, gemini 2개).
- 타임아웃이 나면 같은 모델로 **3번**(최초 1번 + 재시도 2번) 시도한 뒤 다음 모델로 넘어간다 → 모델 하나에 최대 약 91초
- 한 턴에 LLM을 2~3번 부르므로, 제공자가 막히면 **몇 분**까지 늘어날 수 있다. 그 전에 Vercel 함수 시간 제한에 걸리면 화면에는 그냥 오류로 보인다
- NVIDIA 체험 API는 무료 등급이라 대기열에 따라 느려질 수 있다 (11/10 측정 0.4~2.6초 → 오늘 측정 1~6초)

## 5. 배포 서버에서 직접 확인하는 법
`ai/llm/client.py`가 LLM 호출마다 로그를 한 줄씩 남긴다. Vercel → 백엔드 `axa` → Logs에서 `llm `으로 검색한다.
```
llm ok service=chatbot provider=nemotron model=... ms=3551 tokens=4693/197 tools=12 finish=... fallback_from=-
llm fail service=chatbot provider=nemotron model=... ms=30012 error=TransientError fallback_from=-
```
- `ms`가 크고 `llm fail ... TransientError`가 보이면 → 4번 (타임아웃·재시도)
- `fallback_from=nemotron`이 보이면 → 첫 제공자가 실패해서 다음 제공자로 넘어간 것
- `ok` 줄의 `ms`를 다 더해도 전체 시간보다 한참 짧으면 → 콜드 스타트나 DB 문제
- (이 PC에 Vercel CLI가 없고 배포 서버 로그인 정보도 없어서, 이번 점검은 로컬 측정과 `/health` 호출만 했다)

## 7. 배포 서버 로그 확인 (2026-11-25 17:52~17:53, `vercel logs`)
사용자가 배포된 웹에서 4턴을 직접 질문했고, 그 로그를 받아 봤다. Hobby 요금제라 로그는 최근 30분만 남는다.

| 턴 | 질문 | 전체 (요청 시작 → 마지막 LLM 응답) | LLM 호출 (ms · 출력 토큰) |
|---|---|---|---|
| 1 | 대구에서 피부 치료 | 약 15.4초 | 10,256ms · **1,117** (도구 선택) → 5,098ms · 482 |
| 2 | 수성구 여드름 흉터 피부과 | 약 7초 | 4,220 · 238 → 2,672 · 264 |
| 3 | 추천 + 12/4 10시 예약 | 약 12.5초 | 6,046 · 358 → 1,916 · 182 → 4,775 · 347 |
| 4 | 통역 돼요? | 약 12.4초 | 12,316 · **725** (도구 없이 답만) |

- **LLM 외 시간은 턴마다 1초 미만이다.** 요청이 들어온 뒤 LLM 호출이 끝날 때까지가 전체 시간과 거의 같다 → 콜드 스타트·DB·가드레일은 이번 측정에서 원인이 아니었다 (직전에 로그인해서 서버가 이미 켜져 있었음)
- 모든 호출이 nemotron-3.5-super로 성공했다. 실패(`llm fail`)나 다른 모델로 넘어간 기록(`fallback_from`)은 없다
- **출력 토큰이 시간을 결정한다.** "통역 돼요?" 한 줄에 725토큰, 12초. 도구 하나를 고르는 데 1,117토큰, 10초
- 함수가 도는 리전은 **icn1(서울)**이다. `docs/deploy-vercel.md`에는 sin1로 적혀 있어 실제와 다르다. DB(싱가포르)와 리전이 다르지만 이번 측정에서는 영향이 작았다

### 원인: Nemotron의 "생각(reasoning)" 토큰
같은 키로 "통역 돼요?"를 한 번씩 보내 비교했다 (짧은 시스템 프롬프트만 넣음).

| 설정 | 시간 | 출력 토큰 | 그중 reasoning |
|---|---|---|---|
| 기본 | 2,856ms | 304 | **285** |
| `chat_template_kwargs: {"enable_thinking": false}` | 925ms | 16 | 0 |

- nemotron-3.5-super는 **기본으로 답하기 전에 숨은 생각 글(reasoning_content)을 길게 쓴다.** 화면에는 안 보이지만 출력 토큰과 시간에는 모두 들어간다. 배포에서 본 725·1,117토큰도 대부분 이것으로 보인다 (배포 응답의 reasoning 토큰 수는 로그에 없어 미확인)
- 덤: `client.py`가 이 `reasoning_content`를 `message_extra`로 받아, 도구 루프에서 다음 호출에 다시 보낸다 → 입력 토큰도 늘어난다

### 가장 효과 큰 수정 (6절보다 우선)
| # | 방법 | 기대 효과 | 주의 |
|---|---|---|---|
| 0 | nemotron 호출에 **thinking 끄기** (`chat_template_kwargs.enable_thinking=false`) | 호출당 수 초 감소. 한 턴 7~15초 → 대략 절반 이하로 예상 (미측정) | 도구 선택·질문 순서 정확도가 떨어질 수 있음 → `run_scenario`로 다시 검증 필요 |
| 0-1 | `reasoning_content`는 다음 호출에 다시 보내지 않기 | 도구 루프의 입력 토큰 감소 | Gemini의 `thought_signature`는 계속 돌려줘야 함 (지우면 안 됨) |

## 8. thinking 끄기 적용 · 시나리오 평가 (2026-11-25)

## 9. 묻는 횟수 줄이기 (2026-11-26)
턴 하나를 빠르게 하기 어려우니, **기다리는 횟수**를 줄였다. 백그라운드 처리는 맞지 않는다고 판단했다: 예약은 하나씩 되묻는 대화이고, 마지막 [제출]도 사용자가 직접 누른다 (근거: `research/챗봇-에이전트-응답시간-기준-2026-11-26.md`).

### 바꾼 것 (`ai/agent/prompts/orchestrator.py`)
- 전: 빠진 칸(날짜·언어·국적·비자·문의)을 **하나씩** 물음 → 병원을 고른 뒤 초안까지 5~6턴
- 후: 빠진 칸을 **한 메시지에 번호 목록으로** 묻고 "한 줄로 답해도 된다"고 안내. 일부만 답하면 남은 칸만 다시 한 번에 묻는다. 값을 추측하지 않는 규칙은 그대로
- 함께 고친 것: 사용자가 묻기 전에 체류 형태를 먼저 말한 경우("일주일 방문이에요, 첫 번째 병원으로 예약해 줘") 챗봇이 그 말을 기록하지 못하고 계속 되물었다. 이제 최신 메시지에 본인 말로 있으면 그 턴에 바로 기록한다 (`record_residency`가 인용문이 최신 메시지에 있는지 코드로 확인하는 것은 그대로)

# 예약 규칙 — 중복 예약 · 노쇼 (2026-11-26)

외국인 단기 방문객 한 사람이 여러 병원에 상담·예약을 요청할 때 지키는 규칙.
코드: 서버 `backend/src/modules/booking/service.py`(최종 판단) · 화면 `apps/web-platform/src/features/consult/bookingRules.ts`(보내기 전에 미리 막음, 예시 로그인은 여기서만 막힘)
숫자(60분 · 5건)는 두 파일에 같은 값으로 있다 → 바꿀 때 같이 바꾼다.

---

## 1. 용어

| 말 | 뜻 |
|---|---|
| 살아 있는 예약 | 상태가 **확인 대기(pending) · 시간 제안(proposed) · 확정(confirmed)** 인 예약. 거절·취소·만료·방문 완료·노쇼는 빠짐 |
| 처리 전 요청 | 확인 대기 · 시간 제안 (병원 답이나 환자 수락을 기다리는 것) |
| 잡힌 시간 | 확정·시간 제안이면 그 시간 1개, 확인 대기면 **희망 시간 1~3개 전부** (병원이 그중 하나로 확정할 수 있으므로) |

---

## 2. 중복 예약 규칙 (구현됨)

| # | 규칙 | 막는 예 | 오류 코드 |
|---|---|---|---|
| R1 | **시간 간격 60분** — 어느 병원이든 내 다른 살아 있는 예약의 잡힌 시간 앞뒤 60분 안에는 새 요청 불가 | A병원 16:00 확정 → B병원 15:01~16:59 요청 X, 17:00은 가능 | `booking.time_conflict` |
| R2 | **같은 병원 같은 날 1건** — 시간이 달라도 그날 그 병원에 살아 있는 예약이 있으면 새 요청 불가. 시간을 바꾸려면 기존 예약을 **변경** | A병원 12/4 10:00 요청 중 → A병원 12/4 15:00 요청 X | `booking.same_day` |
| R3 | **처리 전 요청 최대 5건** — 여러 병원에 걸어 두고 안 가는 것(노쇼) 방지 | 확인 대기 5건 → 6번째 요청 X | `booking.too_many` |
| R4 | **병원도 겹치게 확정 못 함** — 병원이 확정·시간 제안하려는 시간이 그 환자의 다른 **확정** 예약과 60분 이내면 막고 다른 시간을 고르게 함 | 환자가 A병원 16:00 확정 → B병원이 16:30 제안 X | `booking.patient_conflict` (병원 화면) |
| R5 | **제안 수락도 같은 검사** — 병원이 제안한 시간이 내 다른 확정 예약과 60분 이내면 수락 불가 | | `booking.time_conflict` |

- 바뀐 점: 예전에는 "같은 병원에 처리 전 요청이 있으면 무조건 불가(`booking.duplicate`)"였다 → **다른 날이면 같은 병원에도 요청 가능**으로 풀었다 (사용자 요청 11/26)
- 예약 **변경**은 그 예약 자신과는 비교하지 않는다 (16:00 → 16:30으로 옮기기 가능)
- 다른 사람의 예약과는 비교하지 않는다 (병원의 같은 시간 정원은 병원이 확정 단계에서 판단)
- 시간 비교는 UTC, 날짜(R2)는 한국 날짜 기준
- 서버는 같은 순간에 두 요청이 동시에 들어오는 경우(경쟁 상태)까지 막지는 않는다 — 운영 전 DB 잠금 또는 제약 검토

### 왜 60분인가 (가정값)
대구 시내 이동(택시 20~30분) + 접수 · 상담 시간을 더한 최소 간격. 시술·검진처럼 오래 걸리는 진료가 많아지면 진료 종류별로 늘리는 것을 검토 (예: 시술 120분). 근거 자료 **미확인** — 입점 병원 인터뷰로 확인할 것.

## 3. 노쇼 대응 (제안 — 아직 구현 안 함, 팀 결정 필요)

노쇼는 병원이 메디대구를 쓰는 이유(빈 시간 줄이기)를 직접 깎는다. 막기(예방) → 알리기(리마인드) → 기록(사후) 순서로 제안한다.

### 3-1. 예방 — 신청 단계
| 안 | 내용 | 비용·주의 |
|---|---|---|
| P1 | **처리 전 요청 5건 제한** | 구현됨 (R3) |
| P2 | **방문 일정 입력** — 요청 때 한국 체류 기간(입국·출국일)을 받아 그 밖의 날짜는 못 고르게 | 마이페이지 여행 일정(`tripSchedule.ts`)과 연결 가능 |
| P3 | **확정 전 재확인** — 병원이 확정하면 환자가 "갈게요"를 한 번 더 눌러야 최종 확정 (24시간 안에 안 누르면 자동 취소) | 단계가 하나 늘어남 |

### 3-2. 알림 — 방문 전
| 안 | 내용 |
|---|---|
| N1 | **리마인드 알림** — 방문 48시간 전 · 24시간 전 · 2시간 전 (웹 푸시 · 사이트 알림, 환자 언어) — **구현됨** (아래 3-5) |
| N2 | **알림에 "갈게요 / 취소할게요" 버튼** — 못 오면 미리 취소해서 병원이 그 시간을 다른 환자에게 |
| N3 | **길 안내 함께** — 병원 주소(한국어 원문) · 지도 링크 · 소요 시간 (외국인은 길을 못 찾아 늦는 경우가 많음) |

### 3-3. 기록 — 노쇼 뒤
| 안 | 내용 | 주의 |
|---|---|---|
| H1 | 병원이 대시보드에서 **노쇼 처리**(이미 있음: `no_show` 상태) | |
| H2 | **노쇼 횟수 제한** — 최근 90일 노쇼 2회면 처리 전 요청 한도를 5건 → 1건으로 줄임, 3회면 30일 요청 정지 | 사유 소명(아팠음 등) 받는 창구 필요 · 개인정보 처리방침에 "노쇼 기록 이용" 명시 |
| H3 | **당일 취소도 기록** — 방문 2시간 전 이후 취소는 노쇼에 준해 셈 (횟수 기준은 따로) | |
| H4 | 병원에는 **개인 노쇼 이력을 보여 주지 않음** — 비식별 통계(병원별 노쇼율)만 | 다른 병원 이력 공유는 개인정보 제3자 제공 문제 |

### 3-4. 제안 우선순위 (12/4 시연까지)
1. N1 리마인드 알림 (알림 기능이 이미 있어 붙이기 쉬움)
2. N2 알림 속 "갈게요 / 취소할게요"
3. H2 노쇼 횟수 제한 (규칙만 먼저 문서·화면에, 실제 제한은 운영 데이터 쌓인 뒤)

### 3-5. 리마인드 알림 (N1, 구현됨 2026-11-26)

| 항목 | 내용 |
|---|---|
| 대상 | **확정** 예약만 (확인 대기 · 취소 · 노쇼 · 방문 완료 X), 탈퇴한 환자 X |
| 단계 | 방문까지 남은 시간이 48시간 이하 → `48h`, 24시간 이하 → `24h`, 2시간 이하 → `2h` |
| 중복 방지 | 보낸 기록 = 알림 행(`kind=reminder`, `status=단계`). 같은 단계 · 더 가까운 단계를 보냈으면 다시 안 보냄. 작업이 늦게 돌면 **지금 단계 하나만** 보내고 지난 단계는 몰아 보내지 않음 |
| 보내는 곳 | 사이트 안 알림(종 아이콘) + 웹 푸시(구독한 기기). 잠금 화면 푸시에는 병원 이름을 넣지 않음 (사이트 안 알림에만) |
| 문구 | "○○병원 예약이 2시간 안으로 다가왔어요. 출발 전 위치를 확인해 주세요." 등 6개 언어 (`notify.reminder.*`, `public/sw.js`). '모레·내일'은 실제 날짜와 어긋날 수 있어 "~안으로"로 씀 |
| 누르면 | 예약 관리(`/mypage/bookings`) |
| 코드 | `backend/src/modules/notification/reminders.py` · `POST/GET /api/v1/internal/reminders`(CRON_SECRET) · 마이그레이션 0015(알림 종류에 reminder 추가) · 테스트 `test_reminders.py` |

**돌리는 법 (운영 설정 — 팀 작업 필요)**
- Vercel Cron은 무료 요금제에서 **하루 1번**만 돌 수 있어 2시간 전 알림이 안 됨 → `.github/workflows/reminders.yml`(GitHub Actions)이 **매시 5분** 백엔드를 부름
- 저장소 Settings → Secrets and variables → Actions에 `API_URL`(백엔드 주소) · `CRON_SECRET`(백엔드 환경변수와 같은 값) 등록. 없으면 아무것도 안 하고 끝남
- GitHub 예약 실행은 **기본 브랜치(main)에 합쳐진 뒤**에만 돎. GitHub 사정으로 수십 분 늦을 수 있음 → 2시간 전 알림이 1시간 전쯤 갈 수 있음
- DB에 마이그레이션 0015 적용 필요 (`alembic upgrade head`) — 안 하면 알림 저장 때 오류

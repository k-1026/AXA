## 선택지

### A. 기존 `ai/` 안으로 옮기기 — `ai/llm/client.py` 사용 (추천)

## 결정 (2026-11-17): A + MVP 범위

A로 가면 세 가지 모두 **새로 만들 것이 없음** (이미 `main`에 있음). MVP에서 정할 것은 "어디서 한 번 부르느냐"뿐

| 기능 | 법·팀 규칙상 필수? | 이미 있나 | MVP에서 |
|---|---|---|---|
| 마스킹 | **필수에 가까움** — compliance 2-4 "LLM 호출 전 개인정보 마스킹", 국외이전(해외 LLM, 개인정보보호법 제28조의8)에 넘기는 양을 줄이는 근거 | `ai/llm/safety.py` | 사용자 입력을 받는 **오케스트레이터 앞단에서 1번** (`safety.check`). 서브 에이전트는 오케스트레이터가 만든 글만 받으므로 다시 안 함 |
| 응급 차단 | **법 조문상 필수는 아님** (팀 안전 규칙, compliance 2-4 "응급 고정 문구"). 다만 의료 판단 가드(의료법 제27조 제1항)와 같은 함수에 들어 있음 | 같은 파일, LLM 호출 없이 키워드 검사 (비용 0) | 끄는 게 일이 더 많음 → 같은 `safety.check` 호출로 같이 둠 |
| 재시도·제공자 전환 | 법과 무관, 시연 안정성용 | `ai/llm/client.py` (`with_retry`, Gemini → NVIDIA) | `LLMClient.chat()`만 쓰면 모든 호출(오케스트레이터·서브 에이전트)에 자동 적용 |

→ MVP 작업은 ① 서브 에이전트를 `LLMClient.chat()`으로 부르기 ② 앞단 `safety.check` 1번. 나중으로 미룰 것은 서브 에이전트별 사용량 구분(`service` 이름), 서브 에이전트 결과 검증 정도

## 구현해 보고 다시 판단 (2026-11-17)

- 선택지 A로 환자 챗봇용 멀티 에이전트를 만들어 봄 (`ai-multi-agent` 브랜치 bfc7d67, 테스트 8개). 아래 이유로 **main에 합치지 않고 브랜치를 지움**
- 환자 챗봇 = 지금의 단일 오케스트레이터 유지, 병원 대시보드 = 코드가 순서를 정하는 파이프라인(요약 → 번역 → 답장 초안 → 직원 승인)


**결론: 지금 환자 챗봇에는 맞지 않음.** 단일 오케스트레이터를 그대로 씀

| 근거 | 내용 |
|---|---|
| 지금 단일 오케스트레이터가 잘 됨 | 의도 평가 Gemini 27/27, Nemotron 26/27 (`eval/results/2026-11-10-intent*.md`), 시나리오 8턴 12/12 (`2026-11-11-scenario-*-7a-verify.md`) → 고칠 문제가 없음 |
| 호출 수 | 단일: 8턴에 15~17회(턴당 약 2회). 멀티: 조정자 2회 + 서브 에이전트 2회 이상 → 턴당 약 4~5회. 무료 Gemini 하루 20회면 약 4턴 |
| 맥락 손실 | 서브 에이전트는 대화 기록을 못 봄 → 조정자가 "아까 그 병원(9002)", "12/4 10시" 같은 걸 task에 옮겨 써야 함. 예약 초안처럼 앞 턴 정보가 많은 흐름에서 틀리기 쉬움 |
| 도구 수 | 11개는 한 모델이 충분히 고르는 수. 도구를 나누는 이점은 도구가 수십 개일 때 큼 |
| 속도·평가 | 호출이 직렬로 늘어 답이 느려지고, 오류가 단계마다 쌓여 원인 찾기가 어려움 |

### 더 나은 대안

1. **단일 오케스트레이터 유지 + 도구 묶음 좁히기**: 코드(또는 가벼운 분류)로 이번 턴에 필요한 도구 묶음만 넘김 → 멀티의 장점(도구 선택 정확도)은 얻고, 호출 수·맥락 손실은 없음
2. **정해진 순서는 코드로**: 거주 확인 → 요청서 초안처럼 순서가 정해진 흐름은 LLM 에이전트보다 상태 기계가 안전
3. **멀티 에이전트가 맞는 곳**: 병원 대시보드의 요청 요약·번역·답장 초안 (`ai/agent/tools/summarize_request.py`·`translate.py`·`draft_reply.py`가 비어 있음). 대화가 아니라 작업 단위라 맥락 손실이 없고, 단계별로 다른(싼) 모델을 쓸 수 있음
